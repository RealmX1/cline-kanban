# 高负载下工作区读取与主会话完成事件恢复

实现包含前台读取恢复、普通主会话完成事件持久对账，以及异步 Git 探测。源码验收、固定版本性能实验和真实实例部署后核验分别记录。

## 前台 Diff 读取

`useRuntimeWorkspaceChanges` 复用 `useRecoverableForegroundRead`。一次读取的逻辑期限为 8 秒，最多三次尝试，退避 400／1200 ms。客户端把 AbortSignal 传给独立 tRPC 请求；即使读取方忽略 signal，Promise.race 也结束等待并丢弃迟到结果。事件循环阻塞仍可能使墙钟期限后移。

同一归属只有一个在途读取。版本失效和刷新在读取期间合并补读；任务或视图归属切换取消旧读取。旧数据、错误、queryPhase 和内容相同的引用保留原有语义；跨任务不能沿用前一个任务的 diff。

耗尽预算后停止轮询和状态版本引发的自动读取。`online`、页面重新可见、对应工作区推流重连、人工刷新或归属切换可以开始新一轮。该策略只用于读取；保存、输入、Stop 的未知结果仍须查询已有回执。

客户端取消不能证明服务端已有 Git 子进程退出；后台工作按各自既有生命周期收口。

## 普通主会话完成事件

入口限定为携带投递幂等 key、runtimeSessionIncarnationId 和原始捕获时间的普通主会话 `to_review`：自然 Stop／AfterAgent／agent-turn-complete。子 agent、原始 prompt、用户问答和权限决策沿原有专用体系处理。

`recoverable-hook-lifecycle-event-deliveries.json` 位于对应工作区持久目录。记录只保存身份、捕获时间及生命周期最小语义；当前收到的原始通知正文和 CLI 资源遥测可在本次调用中使用，不能进入恢复记录。恢复通知从已确认的会话事实重构。

持久受理先于 host 暂存确认删除。持久受理与领域应用分开：

| 响应状态 | 含义 |
| --- | --- |
| `durably_accepted_pending_application` | 已持久受理，仍待应用或补证 |
| `application_confirmed` | 同一工作区快照中的领域投影与回执已确认 |
| `superseded_by_newer_session_state` | 已有新输入、换代、关闭或主绑定变化，旧事件不再应用 |
| `permanently_rejected` | 确定拒绝，保留失败历史 |

会话摘要的 `lastAppliedHookReviewLifecycleEventDelivery` 与完成 facet 通过同一次权威快照提交落盘。旧 UI 的整板保存不能撤销运行时回执；同毫秒的伪造标识也不能回滚完成状态。合法的同一回执人工审阅更新仍保留。

完成记录的去重不依赖最近 32 个 key 的内存缓存。已提交而响应丢失、运行时强杀以及后续大量活动后重送，都先查回执。恢复会话历史时保留原始捕获时间、原代和原回合；不把恢复进程的时间记成新的交棒，也不启动 agent。

### 有界恢复与身份门禁

每轮最多三个短尝试。开始应用和尝试预算先持久保存；内存已有回执但快照不可写时，确认写入也受同一预算约束。每 15 秒观察恢复证据，条件未变化不重放领域事件。已知存储错误可通过原快照写链的能力探测补证；探测同工作区单飞，不推进业务 revision。

权威快照已有回执时，补写确认同样受上述预算与失败历史约束。准入恢复指纹还包含投递文件内核锁的无重试能力探测，持锁者无写入释放后也会自动接续；探测不改投递文件。跨运行时的直接重投按原持久受理代际识别恢复，不依赖入口是否来自 host spool。

任务 incarnation、主会话绑定、runtime incarnation、原生身份、回合和新输入水位都在副作用前复核。Stop 自带的同代、同 agent 原生身份可以进入既有身份持久化链补证；其他 agent 的身份不能进入应用。

关闭、搁置、明确 Stop、交接暂停和新输入仍然阻挡旧事件。恢复 observer 只处理可证明的领域事实，不重放同步 harness 指令，不触发付费探索地图维护。

解除搁置保留的 `isShelved:false` 水位允许新完成事件执行。输入接受尚待补证的无工具完成复用现有完成判据。提交与完成同毫秒时，受理前观测到的稳定 `submissionId` 以最小身份字段持久保存，应用与通知都只允许该原提交；受理后出现或替换的输入阻挡旧 Stop。旧记录没有这项观测，或原提交缺少稳定身份时，保留待补证状态，不把相等时间冒充已证明的新输入，也不重复执行领域应用或写盘。恢复扫描在会话、身份或输入水位变化后重新核验；明确推进的新输入、换代及主绑定等门禁仍可终结旧事件。

最多 512 条未终结记录。容量不足或受理写盘失败时不确认丢弃；host 保留原暂存并等待可检测的恢复条件。终结记录持续保留，后续归档必须同时保留去重凭据与失败历史。

通知使用稳定 candidate ID 完成独立对账。`reviewNotificationReconciliationCompleted` 表示对账已结束，包括当前不具备通知资格的情形。通知对账结束、进入通知评估、实际发布和实际送达是不同事实；实际结果以通知档案为准。旧 CLI／host 缺少上述身份字段时继续兼容原行为。单纯返回 host 的 `spooled` 仍只表示内存暂存；本次跨重启保证从 runtime 文件持久受理起算。此前 host 退出或整机断电的可靠性保持未知，不能把内存受理称为持久受理。

通知对账只等待候选的持久登记；模型评估与其并发排队异步继续，不占用同步 hook 响应预算。对账完成仍不代表通知已评估、发布或送达。

生命周期通知显式要求持久登记：档案写入失败、登记服务关闭或同候选仍在登记时保留未完成的对账，不用无档案基础提醒代替确认。仅捕获但尚未登记完成的候选由生命周期记录以稳定 ID 重试；已登记的 eligible 候选由通知档案恢复评估，评估中的候选在重启后进入延期兜底，避免重复模型请求。登记完成但生命周期对账回执尚未保存时，重试仍使用原确认后候选 ID，不重放领域完成事件。

## Git 探测与观测

`loadWorkspaceContext` 所经的 Git 根、分支、默认分支等探测改用异步 `runGit`。工作区身份探测与后台元数据探针共用 `git-concurrency.ts` 中的四并发预算，分支仍即时读取；不会因请求数增长而无界启动探测子进程。

`cline-kanban.workspace-context-git-probe-concurrency-wait` 是内部 Node diagnostics_channel，只在有订阅者时采集等待时间，不包含 prompt、命令正文或身份载荷。基线同步路径没有这条异步队列，零计数不能被解释为基线无阻塞。

性能夹具 `high-load-runtime-workload-profile.integration.test.ts` 默认跳过。显式设置固定的基线 CLI、候选 CLI 和持久证据目录后，通过 `npm run test:guarded` 执行。夹具使用隔离 HOME、CODEX_HOME、CODEX_SQLITE_HOME、Git fixture、随机端口和不调用模型的 agent。

矩阵覆盖 1／10／30 项目、0／1／4 浏览器、安静／持续输出／Git 文件变化／历史增量四种工作负载。先校准刻度扰动，再做五对 AB／BA，保存 CPU、事件循环、API 批次延迟、I/O、同步与异步子进程启动、排队等待及保存／输入／Stop 结果。

实验宿主直接传输约 4 MB 的 JS 会停滞，独立静态服务器和两种 Chrome 都能复现。两组因此由 Playwright 交付各自冻结的构建 assets，API／PTY／WebSocket 仍直连隔离 runtime。该实验不能证明真实实例首次大资源传输已改善。

原生 CPU profile 中的等待样本是经过时间，不能等同 CPU 独占时间。I/O 包装只覆盖主线程 JS 文件 API，子进程计数不覆盖 PTY 原生 spawn 和浏览器辅助进程。保存／输入／Stop 每组仅五个样本，其 P95／P99 取最大值，不代表生产分布。

## 固定版本对照结果

最终 5 对 AB／BA 完整完成 360 个窗口，guarded 测试退出码 0，无未处理错误。排除 CPU profiler 窗口后，五对的场景配对事件循环 P99 中位比改善分别为 77.2%、81.8%、63.3%、75.5%、83.7%；固定读批刻度耗时差异的保守上界为 21.2%。36 个场景的跨配对中位数均改善，因此保留异步探测候选。

进程 CPU／完成批次的变化方向不一致，不宣称 CPU 总消耗下降。保存中位数约 318／320 ms（基线／候选），输入约 42／27 ms，Stop 约 1018／866 ms；小样本只用于核对操作仍成功，不能外推生产尾延迟。

性能证据绑定冻结的基线和候选构建。随后仅修正通知对账字段名称，以及保留 host 首次投递的当前载荷，未改变实测 Git 热路径；最终交接构建另存，实测构建与 source map 持续保留。

## 验证与部署后接续

自动回归覆盖挂起取消、三次预算与恢复事件、失效合并、跨任务隔离、EIO 与确认写入恢复、旧 Stop／新输入、持久容量、隐私投影、快照提交与投影失败、超过 32 个 key 后重送，以及打包 runtime 强杀后的原时间恢复。

Node 22 使用私有原生依赖验证，不重编译共享 SQLite。构建输出也隔离到任务的持久核验目录，避免更新主仓库共享 dist。

真实实例另登记两项只读自动核验：连续三次 Diff 的 8 秒响应预算，以及自然故障与运行时更替后的持久完成记录。脚本不能制造生产故障、重启实例、启动 agent、改用户任务或把缺少记录当成通过。定义、dry-run 与资产目录记录在本任务持久交接材料中。

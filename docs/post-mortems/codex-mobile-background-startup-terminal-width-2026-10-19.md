# 手机后台启动 Codex 的终端列宽与首发挂起

## 现场与证据边界

任务 `94c85` 在 America/New_York 时间 2026-10-18 20:18:43 已启动 Codex；用户在次日
05:20:14.906 打开任务，原始提示词于 05:20:17.546 首次进入原生转录，05:20:22.481 开始回复。
提示词正文完全一致且仅出现一次。这证明延迟发生在进程启动之后；时间关联本身不能证明打开任务就是根因。

历史日志没有初始终端尺寸，不能断言该任务当时就是 1 列。`e0077` 的历史证据是未启动进程，属于更早的阶段，
也不能用本次尺寸修复宣称它已解决。

## 可重复的机制

`resolveAgentTerminalGeometryForTaskSessionSpawn` 对尚未挂载的终端，用视口宽度减去桌面并排 diff 的 360px，
再减终端边框 40px，按 8px 单元格估算列数。390／393px 手机视口因此得到 1 列，430px 得到 3 列。
手机详情页实际将终端与 diff 放在不同 tab，终端使用整页宽度。

独立 Codex CLI 0.163.0 + PTY + headless xterm 对照中，1／3 列启动持续 6 秒都无法识别到输入就绪，
调整为 60 列后立即就绪；20／60 列约 30ms 就绪。Codex Plan Mode 的首条提示词延后到屏幕就绪时才写入，
因此错误尺寸可产生「后台一直等待，打开详情后的 resize 才触发首发」这一完整机制。

修复按既有移动断点选择整页宽度，复用原有边框、单元格及行数估算；实测尺寸仍优先，桌面布局继续保留 diff 空间。
启动诊断增加 `requestedTerminalColumns` / `requestedTerminalRows`；它们是请求值，缺省为 `null`，不冒充实际 PTY 尺寸。

## 验证与版本辨认

回归测试覆盖手机宽度、768／769px 边界、桌面面板限制、实测尺寸优先及软键盘下的最小行数。
真实浏览器检查覆盖 All Projects 同项目、跨项目及单项目对照；不打开详情、不连接 terminal WebSocket，
验收要求原生提示词正文完全一致、仅一次、模式为 plan，且随后收到目标回复。

源码、磁盘构建和进程加载内容须分别核实。调查时部署标记为 `01a6f1c6`（包含旧修复 `5be40404`），
但磁盘 `dist` 后来已重新构建；PID 56127 的启动时间早于这次磁盘构建。没有构建身份凭据时，不能用部署标记、
当前 `main` 或磁盘 source map 直接宣称长驻进程的加载 SHA。部署后脚本读取正在发布的前端 source map，执行其尺寸模块验证移动与桌面分支。

运行方式见 [测试说明](../../test/README.md)。测试使用独立 HOME、Codex 配置和 Git fixture，凭据仅复制到测试目录，结束时清理。

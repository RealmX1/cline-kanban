# Codex RVF 自动收尾的压缩感知确认

此策略预防已经识别的首次过早超时：确认链在可信自动压缩期间继续等待，仍以精确原生用户消息作为送达证明。现有[迟到接受补证](rvf-late-native-closeout-prompt-acceptance-recovery.md)继续处理旧会话、缺失信号、超出预算和历史失败，两者长期并存。

## 启用范围与原生能力

仅对明确来源为 `rvf_automatic_closeout`、且 task/conversation/token/run/handoff/正文摘要全部匹配的 Codex 投递启用。普通聊天、RVF 发起决策点及其他 agent 的策略不变。没有公开的任意加长超时参数。

启动时通过实际二进制的版本与文件身份核验能力；当前验收版本为 Codex `0.164.0`。未知版本保留原配置，不配置新的 `PreCompact`。用户已经覆盖 `hooks.PreCompact`、`hooks.PostCompact` 或 `hooks.state` 时也不启用阶段等待，避免改变自定义 hook 或引入信任审批。扩展已验收版本集合前须重跑原生探针。

新会话确实配置了阶段 hook 才保存能力标记。运行时升级不会给仍存活的旧 TUI 追加 hook；不得为此擅自重启消费者。

原生隔离探针使用实际 Codex、隔离 HOME/config/Git fixture 与本地 provider，测试专用阈值强制触发自动压缩；不访问账号或付费模型。生产函数生成信任哈希，原生侧不绕过 hook 审批。探针分别证明：

- `PreCompact` 在压缩完成前已经提供原生 session/turn；不是压缩完成后追记的开始时间。
- 同步 `PreCompact` hook 仍未返回时，独享控制宿主能够读取同一个进行中的 turn；核验不会与原生压缩互相等待。
- provider 响应被扣留时可以读取同一 turn；完成 hook 保持相同 session/turn/auto 绑定。

这不证明三个历史生产样本的实际压缩阈值、scope、网络耗时或逐 tick 调度。探针使用自定义 provider 的原生压缩路径，不把它的测试阈值当成生产配置。[官方 hook 定义](https://learn.chatgpt.com/docs/hooks)仅作接口参考，已验收版本的启用依据是实际探针。

## 有界计时与接受门禁

| 阶段 | 预算与行为 |
| --- | --- |
| 普通确认 | 15000ms，从首次实际提交阶段起算；未收到可信开始信号时不增加预算 |
| 自动压缩 | 暂停剩余普通预算；多次压缩累计最多增加 300000ms |
| 压缩结束 | 恢复原有剩余普通预算，不重新给 15 秒 |
| 绝对上界 | 首次提交后 315000ms；重复事件、多个阶段和热重启都不能重置 |

原生请求通过 `turn/start` 提交时，首次提交时间取请求前的持久标记；PTY 后备取首次 CR 前的标记。两条通道使用同一个状态模块。压缩期间不再发 CR，不重新粘贴。原生请求一经尝试，断线后只重建查询连接，不再次 `turn/start` 或改走 PTY。

事件必须匹配 workspace、会话、启动代际、独享宿主、原生 session 和相关新 turn。只有 `trigger=auto` 能授予预算。旧 turn、子代理、人工 `/compact`、重复开始/完成、完成先到、以及普通截止后才到的开始事件都不能延长；`task_started` 只用于阶段归属，不是接受证明。

接收时刻决定剩余计时，不追溯挪动已经结算的截止。精确原生 `userMessage` 可以先于完成 hook 结束确认。确认须匹配本次请求的消息关联或返回的新 turn、完整正文和原生会话；提交 hook、输出或压缩本身均不能代替它。

## 持久化、清扫与热接管

注入账本新增可选 `nativeCompactionAwareConfirmation`，包含不可换绑的身份、摘要、首次提交、固定截止、当前阶段、剩余预算、累计压缩等待、revision 和已应用事件 ID。接管后另记核验次数与时刻。没有保存 callback 或新增正文副本。

初次发送必须复核当前 handoff 字节与重建正文。接管只读核验历史提交：优先按原绑定重建正文并复核摘要；模板或路径后来变化时，使用原队列中已经冻结、且摘要与账本一致的唯一正文。已经持久提交的快照不因 handoff 文件后来移动或缺失失效；当前 Stop、run/token/SHA、原生身份和代际约束仍须通过。这条恢复路径不能调用发送。

每次延长等待先通过同一账本锁和 revision CAS 持久化。写入失败不延长预算；终态不可覆盖。PTY host 的接管记录携带同一快照与能力标记，账本仍是跨进程主存储，host 快照迟到不能把新状态倒退。

清扫按单条新快照的有效阶段截止加 5000ms 判定。旧记录不自动获得额外预算，保留原判据。共享账本的所有清扫器必须升级后才可启用；旧清扫器不能理解新截止，混用会提前结算合法等待。本任务只交付源码，不部署。

prompt queue 的启动清扫与持续属主巡检也读取同一账本：只有 `handed_to_transport`、自动收尾来源、精确正文/任务/key 匹配且存在新提交快照的条目，才能继续等待。它不回到队首、不盖人工重确认章；接管写下真实终态后，队列从该结果收敛，避免失去旧内存回调后永久在途或反向镜像失败。

清扫先在队列锁内重读队列。发现已提交自动收尾时，先释放单独队列锁，再由 `lockedFileSystem.withLocks` 按统一路径顺序取得队列与账本两把写锁；联合锁内重新读取最新队列与账本，复核同一 key、正文与绑定，并持锁到队列提交完成。账本普通原子读取本身不加锁，不能独自保证跨存储结算一致性；这里显式持有账本写锁，防止终态或合法截止在读取后变化。镜像在全部锁释放后才取得账本锁，不在联合锁内重入；入队同样先结束账本锁阶段再写队列。普通队列不获取账本锁或增加账本读取。无法读取时保留未知，下次巡检再验。阶段变化延后原截止时，启动复扫会在固定上限内续排，持续巡检另有周期兜底。

独占接管成功后，核验同一原生宿主、session、启动代际、原进程启动时间和绑定记录；只恢复接受观察与结果登记。停机时间计入当时阶段，沿用原截止。截止已过时允许一次只读核对现有接受事实，无证据即收口。暂时读盘失败最多再试两次，不重发消息。

明确 Stop、身份变化、绑定不全或当前收尾已暂停时不恢复执行；保留具体诊断和原记录。confirmed/completed 记录与重复巡检不重新执行。失败 reason 集合不新增：本策略预算耗尽沿用 `submit_confirmation_budget_exhausted`，原有显式与自动迟到补证仍适用；land/base 仍须通过实际 commit、evidence 和祖先门禁。

## 验证与诊断

`kanban task message-status` 可显示同名快照；`[rvf-compaction-confirmation]` 日志记录会话、revision、阶段、预算和截止，不记录正文。无压缩时保持普通路径，旧会话仍可使用迟到补证。

- `38fd3`：保留正常及时确认作为正向对照；没有压缩，不强行进入恢复路径。
- `c4c82`、`1c6e4`、`46d51`：受控调度分别覆盖 117160、129828、120347ms 压缩；同一测试 payload/绑定只改变事件顺序，确认跨过原 15 秒窗口且只提交一次。
- `9c9c1`、`df81c`、`30555`：仍为背景成功样本，没有声称本次独立重放。

回归包含普通/压缩/累计上限、重复和乱序、缺信号、停止/换代、写入失败、CAS 并发、旧记录、两条清扫链、同宿主接管、历史正文恢复及截止后只读核验。仅部署后真实新会话和真实热重启能证明安装状态，隔离测试不勾选部署后验证。
